1. Resumo em 3 frases

O rdn-api é o back-end de uma rede de lanchonetes com múltiplos canais (APP, TOTEM, BALCAO, PICKUP, WEB), construído em Spring Boot 4 / Java 25 com PostgreSQL e Flyway.

Hoje ele tem duas camadas prontas: o domínio (regras de pedido, pagamento, estoque, fidelidade) e a infraestrutura de persistência (entidades JPA, mappers, repositórios, migrations e DER).

Ainda não existe camada application nem api: o modelo grava e lê do banco com teste verde, mas nenhum endpoint HTTP está exposto.

3. Explicação por arquivo

3.1 Order.java — o agregado do pedido

src/main/java/com/rdn/rdn_api/domain/Order.java

É a raiz do agregado: quem manipula itens, total, status e cancelamento passa por aqui. Não conhece JPA, HTTP nem banco; depende apenas de OrderItem, MenuItem, User, Branch e dos enums OrderStatus e SalesChannel.

Fluxo de execução

  1. O caso de uso cria Order, chama addItem() para cada item e calculateTotal().
  2. changeStatus() valida a transição antes de gravar o novo estado.
  3. cancel() delega para changeStatus(CANCELLED) e só então grava o motivo.

Anotações e imports que importam

Nenhuma anotação JPAMantém o domínio puroO mapeamento vive em OrderJpaEntity

Linha a linha

private static final Map> ALLOWED_TRANSITIONS = // (1)
        Map.of(
                OrderStatus.RECEIVED, Set.of(OrderStatus.PREPARING, OrderStatus.CANCELLED), // (2)
                OrderStatus.PREPARING, Set.of(OrderStatus.READY, OrderStatus.CANCELLED),
                OrderStatus.READY, Set.of(OrderStatus.DELIVERED, OrderStatus.CANCELLED),
                OrderStatus.DELIVERED, Set.of(), // (3)
                OrderStatus.CANCELLED, Set.of());
  1. static final porque a tabela de transições é a mesma para todo pedido — não é estado de instância.
  2. Map.of + Set.of criam coleções imutáveis; qualquer tentativa de alterar em runtime lança UnsupportedOperationException, o que protege a regra contra mutação acidental.
  3. Set.of() vazio significa "estado final": DELIVERED e CANCELLED não têm saída.
public BigDecimal calculateTotal() {
    BigDecimal sum = BigDecimal.ZERO; // (1)
    for (OrderItem orderItem : items) {
        sum = sum.add(orderItem.calculateSubtotal());
    }

    BigDecimal discount = discountAmount == null ? BigDecimal.ZERO : discountAmount; // (2)
    if (discount.signum() < 0) {
        discount = BigDecimal.ZERO;
    }
    if (discount.compareTo(sum) > 0) { // (3)
        discount = sum;
    }

    totalAmount = sum.subtract(discount);
    return totalAmount;
}
  1. BigDecimal é imutável: sum.add(...) devolve um novo objeto, por isso a reatribuição é obrigatória.
  2. Guarda contra null — discountAmount é BigDecimal (wrapper), que aceita null, diferente de double.
  3. compareTo e não >: BigDecimal não deve ser comparado com operadores, porque 1.0 e 1.00 são equals diferentes mas compareTo iguais. Aqui o objetivo é limitar o desconto à soma dos itens, garantindo total ≥ 0 — o que também protege a constraint ck_orders_total do banco.
public void changeStatus(OrderStatus newStatus) {
    if (newStatus == null) {                                   // (1)
        throw new IllegalArgumentException("status e obrigatorio");
    }

    if (status == null) {                                      // (2)
        if (OrderStatus.RECEIVED != newStatus) {
            throw new IllegalStateException("pedido deve iniciar em RECEIVED");
        }
        this.status = newStatus;
        return;
    }

    if (!ALLOWED_TRANSITIONS.getOrDefault(status, Set.of()).contains(newStatus)) { // (3)
        throw new IllegalStateException(
                "transicao de " + status + " para " + newStatus + " nao permitida");
    }

    this.status = newStatus;
}
  1. IllegalArgumentException para entrada inválida do chamador; IllegalStateException para estado atual incompatível. Essa distinção permite à camada de API traduzir a primeira em 400/422 e a segunda em 409.
  2. Pedido recém-criado não tem status: só pode nascer em RECEIVED. Sem esse bloqueio, seria possível criar pedido já DELIVERED.
  3. getOrDefault(status, Set.of()) evita NullPointerException caso apareça um status fora do mapa (ex.: enum novo sem regra cadastrada) — nesse caso a transição é negada, que é o comportamento seguro.
public void cancel(String reason) {
    changeStatus(OrderStatus.CANCELLED); // (1)
    this.cancellationReason = reason;   // (2)
}
  1. Delegar impede duplicação da regra: cancelar um pedido DELIVERED agora falha.
  2. O motivo só é gravado depois da validação; se a transição for negada, nada é alterado.

Padrões aplicados

  • State machine: changeStatus (linha 124) com tabela declarativa de transições.
  • Guard clause: if (newStatus == null) na linha 125.
  • Rich domain model: regra dentro da entidade, não no service.
  • Encapsulation: setStatus continua público (linha 192) apenas para reidratação por mapeadores — é o ponto de atenção número 1 do projeto.

3.2 Payment.java — a tentativa de pagamento

src/main/java/com/rdn/rdn_api/domain/Payment.java

Representa uma tentativa de cobrança no provedor simulado, não "o pagamento do pedido". Isso permite histórico: pedido pode ter uma tentativa DECLINED e outra APPROVED. Não conhece JSON, HTTP nem PaymentGateway.

Fluxo de execução

  1. Caso de uso cria Payment (status nasce PENDING, requestedAt = agora).
  2. Chama o gateway mock e recebe um resultado.
  3. Converte o resultado em markApproved, markDeclined ou markFailed.

Anotações e imports que importam

ElementoO que fazPor que está aqui
PaymentStatus status = PENDING (linha 29)Estado inicial no campoMesmo via reflexão/JPA, um pagamento novo nunca nasce em estado final
BigDecimal (linha 25)Valor monetárioAlinhado a NUMERIC(10,2) em payments.amount
LocalDateTime (linhas 37-39)Marcas de tempoMapeia para TIMESTAMP sem timezone no Postgres

Linha a linha

public Payment(Order order, BigDecimal amount, PaymentMethod method, String idempotencyKey) {
    if (amount == null || amount.signum() <= 0) {                 // (1)
        throw new IllegalArgumentException("amount deve ser positivo");
    }
    if (idempotencyKey == null || idempotencyKey.isBlank()) {     // (2)
        throw new IllegalArgumentException("idempotencyKey e obrigatoria");
    }

    this.order = order;
    this.amount = amount;
    this.method = method;
    this.idempotencyKey = idempotencyKey.trim();                  // (3)
    this.status = PaymentStatus.PENDING;
    this.requestedAt = LocalDateTime.now();
}
  1. signum() devolve -1, 0 ou 1: é a forma idiomática de testar sinal de BigDecimal sem aritmética.
  2. isBlank() cobre "" e " " — diferente de isEmpty(), que aceitaria espaços.
  3. trim() normaliza a chave antes de gravar, porque a coluna é UNIQUE: "abc" e "abc " precisam colidir, senão a idempotência vaza.
public void markApproved(String transactionId, String rawResponse) {
    requirePending();                       // (1)
    this.status = PaymentStatus.APPROVED;
    this.gatewayTransactionId = transactionId;
    this.gatewayRawResponse = rawResponse;  // (2)
    this.processedAt = LocalDateTime.now(); // (3)
}
  1. Guarda centralizada: impede transformar APPROVED em DECLINED se o webhook chegar duas vezes.
  2. Guardar o payload bruto é requisito de auditoria: sem ele, não há como investigar divergência de valor depois.
  3. processedAt é preenchido apenas quando há resposta do provedor — payments.processed_at é nullable exatamente por isso.
private void requirePending() {
    if (status != null && PaymentStatus.PENDING != status) {
        throw new IllegalStateException(
                "pagamento ja finalizado com status " + status + " e nao pode ser alterado");
    }
}

O status != null protege contra objeto reidratado sem status (mapeador ou banco legado); nesse caso, permitir a transição é mais seguro do que estourar NullPointerException.

Padrões aplicados

  • Factory por construtor com validação: Payment(...) (linha 54) garante que não existe pagamento inválido em memória.
  • Guard clause / template method privado: requirePending (linha 129) chamado pelos três métodos de transição.
  • Estado explícito: status como campo, nunca derivado de "processado ou não".

3.3 OrderJpaEntity.java — a tradução relacional

src/main/java/com/rdn/rdn_api/infrastructure/persistence/entity/OrderJpaEntity.java

Existe porque Order não tem anotação JPA. Aqui ficam @Entity, @Column, @Table e as associações. Quem depende dele é o repositório e o OrderMapper.

Fluxo de execução

  1. OrderMapper.copyScalarsToEntity() copia campos simples.
  2. O adaptador resolve customer, branch e menuItem (associações) via repositórios.
  3. OrderJpaRepository.save() persiste a árvore, em cascata para os itens.

Anotações e imports que importam

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "customer_id")

@ManyToOne(optional = false, fetch = FetchType.LAZY)
@JoinColumn(name = "branch_id", nullable = false)

  1. Sem optional = false, o cliente é opcional — pedido de totem pode não ter usuário identificado.
  2. Filial é obrigatória: pedido sem unidade não existe no domínio de uma rede de lanchonetes, e a FK garante isso no banco.
@OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true,
        fetch = FetchType.LAZY)
private List items = new ArrayList<>(); // (1)
  1. Três decisões em uma linha: inicializar com new ArrayList<>() evita NullPointerException no add antes do carregamento; cascade = ALL faz save(order) salvar os itens; orphanRemoval = true remove do banco o item retirado da lista — sem isso, order.getItems().remove(x) não geraria DELETE.

Padrões aplicados

  • Persistence Entity separada do Domínio (linha 35).
  • Lazy loading + @EntityGraph no repositório para o caso de leitura.
  • Cascade + orphanRemoval como unidade de trabalho do agregado (linha 73).

3.4 V1__schema.sql — o contrato do banco

src/main/resources/db/migration/V1__schema.sql

É a fonte de verdade do schema: ddl-auto=validate confere se o mapeamento JPA bate com este DDL, mas nunca cria tabela. É versionado porque V1 roda uma única vez no histórico do Flyway.

Fluxo de execução

  1. A aplicação sobe e o Flyway lê db/migration.
  2. Executa V1 (schema) e depois V2 (seed) na ordem numérica.
  3. Grava o histórico em flyway_schema_history; se V1 já rodou, não roda de novo.

Linha a linha

CONSTRAINT pk_orders PRIMARY KEY (id),
CONSTRAINT uk_orders_idempotency_key UNIQUE (idempotency_key),   -- (1)
CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id) REFERENCES users (id),
CONSTRAINT fk_orders_branch FOREIGN KEY (branch_id) REFERENCES branches (id),
CONSTRAINT ck_orders_channel CHECK (origin_channel IN ('APP', 'TOTEM', 'BALCAO', 'PICKUP', 'WEB')), -- (2)
CONSTRAINT ck_orders_status CHECK (status IN ('RECEIVED', 'PREPARING', 'READY', 'DELIVERED', 'CANCELLED')),
CONSTRAINT ck_orders_total CHECK (total_amount >= 0),             -- (3)
CONSTRAINT ck_orders_discount CHECK (discount_amount >= 0)
  1. UNIQUE em NULL é permitido no SQL (vários pedidos com chave nula); a unicidade só vale para valores preenchidos. É o que queremos: nem todo pedido tem chave de idempotência mandada pelo cliente.
  2. Repetir o enum no CHECK é redundância intencional: protege contra escrita direta no banco (script, DBA, outro serviço) que não passou pelo Java.
  3. O CHECK é a última linha de defesa do invariante que calculateTotal() já garante — se alguém inserir manualmente um total negativo, o banco recusa.
CONSTRAINT fk_order_items_order FOREIGN KEY (order_id) REFERENCES orders (id) ON DELETE CASCADE, -- (1)
CONSTRAINT ck_order_items_quantity CHECK (quantity > 0),   -- (2)
CONSTRAINT ck_order_items_unit_price CHECK (unit_price >= 0),
CONSTRAINT ck_order_items_subtotal CHECK (subtotal >= 0)
  1. ON DELETE CASCADE no banco + orphanRemoval no JPA cobrem caminhos diferentes: JPA apaga quando o objeto sai da lista, o banco apaga quando o pedido é deletado por SQL.
  2. quantity > 0 espelha a validação de OrderItem: item com quantidade zero geraria linha de pedido sem sentido contábil.
CREATE TABLE payments (
    ...
    idempotency_key VARCHAR(80) NOT NULL,     -- (1)
    requested_at TIMESTAMP NOT NULL,
    processed_at TIMESTAMP,
    CONSTRAINT uk_payments_idempotency_key UNIQUE (idempotency_key),
    CONSTRAINT ck_payments_amount CHECK (amount > 0)
);
  1. Aqui a chave é NOT NULL (diferente de orders), porque toda tentativa de pagamento precisa ser idempotente — repetir a chamada ao gateway não pode gerar duas cobranças.
  2. TIMESTAMP sem timezone, não TIMESTAMPTZ: o Hibernate mapeia LocalDateTime para timestamp por padrão. Usar timestamptz faria ddl-auto=validate falhar na inicialização.

Índices (linhas 108-111): origin_channel, status, branch_id e created_at existem porque são exatamente os filtros do roteiro (?canalPedido=, status, unidade, período). Índice sem consulta correspondente é custo de escrita sem retorno.

Padrões aplicados

  • Versioned migrations (Flyway).
  • Constraint-driven design: PK, UK, FK e CHECK nomeados, o que facilita identificar a violação no log.
  • Fail fast no banco como complemento, não substituto, da validação de domínio.

5. Conceitos-chave para fixar

  1. Agregado (Aggregate): conjunto de objetos tratados como unidade — Order comanda os OrderItem.
  2. Idempotência: repetir a mesma requisição produz o mesmo efeito — garantida por idempotency_key em duas tabelas e pelo requirePending() de Payment.
  3. @Enumerated(STRING): persiste o nome do enum; ORDINAL grava a posição e quebra se a ordem mudar.
  4. Máquina de estados: transições válidas declaradas como dados — ALLOWED_TRANSITIONS.
  5. @Embeddable: objeto sem tabela própria, colunas embutidas no dono — AddressEmbeddable.
  6. Query derivada: nome do método gera o SQL — findByOriginChannelAndStatus.
  7. ddl-auto=validate: o Hibernate confere o schema e falha se divergir, mas nunca altera.
  8. Cache de primeiro nível: o EntityManager devolve a instância em memória; por isso entityManager.clear() é obrigatório para provar persistência.

6. Erros comuns

  1. Se você usar @Enumerated sem EnumType.STRING, o banco grava 0,1,2…; no dia em que alguém inserir um valor no meio de OrderStatus, todos os pedidos antigos passam a ter o status errado, porque o CHECK do banco espera nomes.
  2. Se você chamar order.setStatus(...) em vez de changeStatus(...), a máquina de estados é ignorada e um pedido DELIVERED pode "voltar" para PREPARING — o setStatus público existe só para os mapeadores reidratarem objetos.
  3. Se você remover o entityManager.clear() do teste, o findById devolve o objeto do cache L1, o SELECT nunca executa e o teste passa mesmo com o mapeamento quebrado.
  4. Se você declarar TIMESTAMPTZ no DDL para um campo LocalDateTime, a aplicação nem sobe: ddl-auto=validate compara os tipos e aborta o contexto.
  5. Se você trocar BigDecimal por double, 2 × 25.90 pode virar 51.799999999999997 e a CHECK/teste de total falha — dinheiro exige decimal.
  6. Se você esquecer orphanRemoval = true, remover um item da lista em memória não gera DELETE, e o pedido volta do banco com item fantasma.

7. Exercícios de fixação

Exercício 1 — prever o comportamento

Qual é o resultado de order.changeStatus(OrderStatus.READY) num Order recém-criado (status null)? E de changeStatus(OrderStatus.CANCELLED) também num recém-criado?

Gabarito READY lança IllegalStateException("pedido deve iniciar em RECEIVED"): com status null, o único destino aceito é RECEIVED (linha 129 de Order.java).

CANCELLED também lança, pelo mesmo motivo. A regra "cancela a partir de qualquer estado não final" pressupõe que já exista um estado atual — um pedido que nunca nasceu não pode ser cancelado. Se o requisito fosse permitir cancelar antes do RECEIVED, essa linha 130 teria de ser ajustada.

Exercício 2 — escrever um teste

Escreva um teste que prove que InventoryItem.deductStock recusa retirar mais do que o saldo e que isAvailable() fica false quando o saldo cai ao limite mínimo.

Gabarito 
@Test
void recusaSaidaMaiorQueOSaldoEIndicaIndisponibilidade() {
    InventoryItem item = new InventoryItem();
    item.setQuantityOnHand(new BigDecimal("10.000"));
    item.setMinimumThreshold(new BigDecimal("5.000"));

    assertThat(item.deductStock(new BigDecimal("11.000"), "teste")).isFalse();
    assertThat(item.getQuantityOnHand()).isEqualByComparingTo("10.000");

    assertThat(item.deductStock(new BigDecimal("5.000"), "teste")).isTrue();
    assertThat(item.getQuantityOnHand()).isEqualByComparingTo("5.000");
    assertThat(item.isAvailable()).isFalse();
}
O que o teste prova: deductStock devolve false e não altera o saldo quando falta estoque; e isAvailable() usa compareTo(...) > 0, ou seja, saldo igual ao mínimo já é indisponível. Se alguém trocar > por >=, o teste quebra.

Exercício 3 — alterar a regra sem quebrar o banco

Suponha que a cozinha precise de um estado PARTIALLY_READY entre PREPARING e READY. Liste todos os pontos que precisam mudar, do domínio ao banco.

Gabarito

9. Pontos de atenção e próximo passo

Riscos e dívidas técnicas

  1. Order.setStatus público (linha 192) permite burlar a máquina de estados. Ideal: torná-lo protected/package-private ou mover a reidratação para um construtor específico do mapper.
  2. Camadas application e api vazias: o projeto ainda não é uma API — nenhum endpoint, nenhum DTO, nenhum tratamento de erro padronizado.
  3. Mappers sem consumidor: foram escritos para uso dos adaptadores de repositório, que ainda não existem. Hoje ninguém chama OrderMapper.
  4. Seed sem usuários: V2 cria apenas catálogo e estoque; users está vazio, então não há como logar.
  5. V1 nunca rodou em PostgreSQL real: validado apenas em H2 modo PostgreSQL. Rodar docker compose up -d + mvnw spring-boot:run é obrigatório antes da entrega, para confirmar o ddl-auto=validate.
  6. AuthSession guarda apenas hash: AuthSessionMapper.toDomain devolve token nulo por design — a validação de sessão terá de ser feita por comparação de hash, não reidratando o token.
  7. Promotion não participa do pedido: falta a coluna/entidade de vínculo (order_promotions) para registrar qual promoção foi aplicada.
Próximo passo recomendado: implementar a camada application do Fluxo A (CriarPedido, RegistrarPagamentoMock, AtualizarStatus), ainda sem HTTP, com testes de caso de uso sobre os repositórios já existentes — é o que transforma "modelo que persiste" em "fluxo que funciona".
